# 智能小蚁测试环境一键更新

## 目标

研发提交客服代码后，后端在测试服务器执行一条命令完成拉取、安装、构建与重启。客服与官网在同一台服务器，但部署操作仅限客服项目目录和客服 PM2 进程。

## 首次接入（后端一次完成）

1. 创建智能小蚁的私有 Git 仓库；研发将当前项目代码推送到该仓库。`.env.local`、`.env.production.local`、`node_modules`、`.next` 和部署 ZIP 不进入仓库。
2. 为测试服务器配置该仓库的只读 Deploy Key，在客服专用目录克隆仓库。不要将官网代码或服务配置放进客服仓库。
3. 将现有的 `.env.production.local` 放在客服目录；此文件只保留在服务器。
4. 使用 PM2 运行客服的 `npm run start`，记下客服进程名。脚本会核对这个 PM2 进程的工作目录，只有与客服仓库根目录相同时才继续。
5. 在客服目录执行 `chmod +x scripts/deploy-staging.sh`。

若目前客服目录是通过 ZIP 部署的，可先由后端确认现有运行路径与 PM2 进程，再迁移为 Git 检出目录。迁移时保留服务器上的环境变量文件，并让 Nginx 继续代理原来的客服端口 `8081`；官网和后端服务无需改动。

## 每次更新

研发把修改推送到约定的测试分支后，后端在客服目录运行：

```bash
./scripts/deploy-staging.sh <客服 PM2 进程名>
```

脚本依次执行 `git pull --ff-only`、`npm ci`、`npm run build`、`pm2 restart`，然后确认 PM2 状态为 `online`。若仓库目录、进程工作目录或本地代码状态不符合预期，脚本会停止，不会重启其他服务。

部署完成后打开测试站点，强制刷新并发送一条咨询消息。若构建失败，先查看命令输出；不要仅重启 Nginx 或用旧 ZIP 覆盖 Git 目录。

## 后续自动化

人工一键更新稳定后，可以在测试分支提交时用 GitHub Actions 触发同一部署脚本。自动化仍应只访问客服目录、只重启客服进程；上线前由后端确认服务器访问方式和发布权限。
